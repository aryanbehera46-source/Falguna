## Scope

The 29-section specification asked for a Digital Workforce (general-purpose task orchestration reusing the existing worker-framework pattern, across research, browser/API/computer execution, documents, spreadsheets, email/admin, and recurring workflows) plus a Media/Growth Engine (brand-aware content pipeline from research through publish, analytics, and growth experiments) layered on top of TTT HQ, built in five internal passes (A–E) without stopping between passes absent a genuine architectural, credential, legal, or safety blocker. All five passes are complete. TTT's existing business-control surfaces (Boardroom, Backlog, Needs Aryan, Revenue Hunter, Sales Manager, Outbound, Onboarding, Billing, Account Management, Sales Ops) were not moved into Falguna and were not rebuilt — the Digital Workforce and Media Engine are new, additive modules that plug into the same `WorkforceOrchestrator`/`WorkforceWorker` pattern, the same Needs Aryan queue, and the same TTT HQ single-page app, per instruction.

No genuine blocker required stopping mid-build. Two real bugs were found and fixed along the way (an orchestrator escalation gap and an ffmpeg text-escaping bug — see Errors and fixes), and one structural HTML bug was introduced and caught by this build's own verification pass before it reached the Mac (see below) — none of these needed Aryan; they were fixed as part of ordinary QA.

## Architecture by pass

**Pass A — Digital Workforce core (`falguna/workforce.py`):** `WorkforceWorker` ABC (`supports(task_type)` / `execute(task) -> WorkerResult`), a `WorkforceTaskStore` with a 9-state task lifecycle (CREATED → PLANNING → READY → EXECUTING → VERIFYING → COMPLETED/FAILED/BLOCKED/NEEDS_ARYAN → CANCELLED), and a `WorkforceOrchestrator` that routes a task to the first registered worker whose `supports()` returns True — the orchestrator never hardcodes a task_type→worker map. `WorkerResult.__post_init__` raises if `status="COMPLETED"` is reported without non-empty `evidence`, so no worker can silently claim completion. A worker's own `BLOCKED`/`FAILED` result becomes a real consequence (an escalation to Needs Aryan, or a bounded retry up to `max_retries`), never a silently-dropped state.

**Pass B — Browser/Documents/Admin workers (`falguna/workforce_workers.py`, `falguna/documents.py`, `falguna/email_admin.py`, `falguna/recurring_workflows.py`):** `ResearchWorker`, `BrowserWorker`, `ContentWorker`, `DataWorker`, `DocumentWorker`, `SpreadsheetWorker`, `EmailAdminWorker` — seven workers covering document/spreadsheet creation, email drafting, and browser/computer-use task intake. `BrowserWorker` uses the same channel/adapter pattern as the pre-existing `application_executor.py`: `ManualBrowserChannel` (the honest default — always `BLOCKED`, no real adapter exists) and `SimulatedBrowserChannel` (test/QA-only, evidence explicitly labeled `simulated: true`, never reachable from ordinary construction). `RecurringWorkflowStore` is a lightweight schedule definition, not an OS-level daemon: `run_due()` creates a real Workforce Task when a schedule is due and advances `next_due_at`; nothing executes a task by itself.

**Pass C — Media Production Engine (`falguna/media.py`, `falguna/media_providers.py`, `falguna/video_pipeline.py`, `falguna/media_agents.py`):** `BrandStore`/`CampaignStore`/`ContentStore` (a 14-state content pipeline: RESEARCH → IDEA → CONTENT_PLAN → SCRIPT → VISUAL_PLAN → ASSET_CREATION → VOICE → VIDEO_EDIT → CAPTIONS → THUMBNAIL → APPROVAL → PUBLISH → ANALYTICS → LEARN, CANCELLED reachable from every pre-terminal state) and a versioned `ScriptStore` that never mutates a prior version. `MediaProviderRegistry` routes each asset type (image/video/voice/music/editing) to a provider honestly labeled `local_free`, `external_api`, or `unavailable` — per the free-first cost policy, no paid provider exists in this build. Two genuinely real, free, local capabilities were found and wired in: `LocalPillowImageProvider` (real PNG generation via Pillow) and `LocalFliteVoiceProvider` (real speech synthesis via ffmpeg's bundled `flite` TTS filter, zero cost). Video generation from a prompt and original music composition have no free/local capability and correctly return `UnavailableProvider` rather than being faked. `VideoPipeline.assemble()` does real ffmpeg-based slideshow assembly from real images plus optional audio (concat demuxer, aspect-ratio scale/pad, ffprobe-verified export metadata), real `.srt` captions computed from actual scene durations — explicitly video *assembly*, never claimed as AI video generation. Seven `WorkforceWorker`-compatible media agents (`ContentStrategistAgent` through `ThumbnailAgent`) drive the content pipeline forward as a side effect of doing one real step each, reusing the exact same worker framework as Pass A/B rather than a parallel one.

**Pass D — Publishing/Analytics/Growth (`falguna/publishing.py`, `falguna/analytics_growth.py`, three more media agents):** A publication lifecycle (DRAFT → READY → AWAITING_APPROVAL → APPROVED → PUBLISHING → PUBLISHED/FAILED, with FAILED→APPROVED for retry and FAILED→PUBLISHED reserved for the manual-fallback path). `ManualPublishingChannel` — the only channel ever reachable over HTTP — always `BLOCKED` (no real platform adapter exists yet); a blocked attempt lands the publication in `FAILED` and escalates a `publish_approval` Needs Aryan item rather than silently doing nothing. `mark_published_manually()` is the one honest way to reach `PUBLISHED` without a real channel: it requires non-empty real evidence (e.g. an actual post URL a human supplies) and refuses on empty evidence. `SimulatedPublishingChannel` exists for tests only, always labels its evidence `simulated: true`, and is deliberately never exposed over any HTTP route. `AnalyticsStore.record()` requires a real, named `source`; `.list(real_only=...)` and `GrowthAgent.recommend()` filter out anything whose source contains "simulated" before computing an engagement rate against fixed, disclosed thresholds (≥10% → repeat, 3–10% → test, <3% → stop) — no invented confidence intervals, and an honest `insufficient_data` result when there is nothing real to compute from yet.

**Pass E — TTT HQ integration (`falguna/ttt_hq.py`, `falguna/hq_web.py`):** `workforce_media_today_signals()` (new, additive, read-only) feeds five new panels into the existing Today dashboard: blocked/escalated workforce tasks, media items pending approval, content due to publish soon, publishing failures, and strong growth signals (content whose `GrowthAgent` recommendation was `repeat`). `_build_workforce_orchestrator()` wires one orchestrator with all 17 workers (7 Digital Workforce + 10 Media agents) so `/api/wf/tasks/<id>/execute` drives any registered task_type through the identical execution path used everywhere else. ~30 new GET/POST routes were added for tasks, recurring workflows, documents, emails, brands, campaigns, content, scripts, assets, publications, analytics, and growth experiments. Six new read-only UI sections (Workforce Tasks, Recurring Workflows, Brands, Content Calendar, Publishing, Growth Experiments) were added to the existing single-page app's nav/view pattern — deliberately read-only, since every approval action (`workforce_action_approval`, `publish_approval`, `cost_approval` — all three new Needs Aryan kinds) is already handled generically by the pre-existing Needs Aryan queue UI, which needed zero new code.

## A structural bug introduced and caught during this build's own QA

While adding the six new nav items, five new Today-view sections, and six new view divs to `HQ_INDEX_HTML`, a `</div>` that should have closed the page's outer `.col` wrapper only *after* the six new view divs was accidentally left in place immediately after the pre-existing last view (`view-rhSettings`) instead — leaving the new views structurally outside `.col` and leaving the true trailing `</div>` (meant to close the outer `.app` wrapper) orphaned. This was caught before ever reaching the Mac: a tag-balance check (Python's `html.parser`, with `<script>...</script>` content stripped since JS-template-embedded markup isn't real static HTML) found the div stack ended unbalanced; tracing it to the exact line (a premature `</div>` between `rhRequalifyResult` and the new `view-wfTasks` div) confirmed a genuine bug, not a pre-existing artifact. Fixed by removing that one premature `</div>` — verified afterward that `.col` now wraps all 18 views (was 12), the whole page's div tags balance exactly (142 open / 142 close, final depth 0), and the full `test_hq_web.py` suite (25 tests) still passes.

## External Action Policy — REAL vs SIMULATED vs UNAVAILABLE, enforced in code

- **REAL**: task lifecycle tracking and orchestration, document/spreadsheet creation, email drafting, recurring-workflow scheduling, brand/campaign/content bookkeeping, script versioning, image generation (Pillow), voice synthesis (ffmpeg+flite), video slideshow assembly and caption generation (ffmpeg/ffprobe), publication lifecycle tracking, analytics recording (from a real, named, human or eventually integration source), and growth-recommendation computation are all genuinely live code, not mocked.
- **SIMULATED**: `SimulatedBrowserChannel` and `SimulatedPublishingChannel` are the only adapters anywhere in this build that can report a fabricated `SENT`/`PUBLISHED`; both are gated behind explicit construction that no ordinary runtime call ever performs, both label their evidence `simulated: true`, and neither is ever reachable from an HTTP route — `/api/media/publications/<id>/publish` always uses `ManualPublishingChannel`.
- **UNAVAILABLE / honest gap**: real browser/computer-use automation, AI video generation from a prompt, original music composition, and real publishing to any external platform all correctly resolve to `BLOCKED`/`UNAVAILABLE` and escalate to Needs Aryan rather than being faked. No paid API adapter exists anywhere in this build, per the free-first cost policy — `MediaProviderRegistry` has no `external_api` provider registered; if one is added later, `MediaAssetStore.total_cost()` already tracks real dollar cost per content item (currently always $0, since nothing paid is wired in).

## Autonomy and Needs Aryan policy

Everything that hits a real capability gap, a real external action, or a real cost stops for Aryan. Concretely: a task whose type has no registered worker is now escalated (this was the one real orchestrator bug found and fixed — see below), not left silently `BLOCKED`; a worker's own `BLOCKED`/`FAILED` result escalates via the same generic `workforce_action_approval` kind; every publication needs an owner decision before it can even attempt to publish (`publish_approval`), and a failed real-channel attempt escalates again rather than silently retrying; a future paid media provider would escalate via `cost_approval` (the kind already exists in `NEEDS_ARYAN_KINDS`, unused today because nothing paid is wired in). What is genuinely autonomous today: task creation, planning/routing, document/spreadsheet/email drafting, recurring-workflow scheduling, the entire content pipeline's state bookkeeping, real local image/voice generation, real video assembly, script versioning, analytics recording and growth-recommendation computation — everything short of a real external action or real spend.

## Errors and fixes

**Orchestrator escalation gap (`falguna/workforce.py`):** `plan()` correctly transitioned an unroutable task (no registered worker for its task_type) to `BLOCKED`, but `execute()` then raised `WorkforceError` instead of returning the task's honest state, and the unroutable case was never escalated to Needs Aryan the way a worker's own `BLOCKED` result is. Fixed: `plan()` now also creates a `workforce_action_approval` Needs Aryan item and transitions to `NEEDS_ARYAN`; `execute()` now returns the task directly when `plan()` leaves it `BLOCKED`/`NEEDS_ARYAN` instead of raising. Covered by three regression tests at three layers (unit, worker-integration, and real-HTTP).

**ffmpeg lavfi text-escaping bug (`falguna/media_providers.py`):** ffmpeg's lavfi filtergraph parser treats `:`, `,`, `[`, `]` as syntax characters even inside single-quoted `flite=text='...'` option values (confirmed directly against the `ffmpeg` CLI — ordinary punctuation like a colon or a bracketed aside crashed synthesis). Fixed via a `_escape_lavfi_text()` helper that backslash-escapes those characters plus backslash and single-quote before building the ffmpeg command. Regression test added and verified against a real synthesized WAV.

**Mac push gap — `falguna/store.py` (caught during this Pass E deployment, not a pre-existing bug):** the new table names were added to `falguna/schema_sqlite.sql` and to `StateStore.create()`'s table allowlist in `falguna/store.py`, but the initial Mac push only copied the 26 files directly named in this build's own file list — `store.py` and `schema_sqlite.sql` were missed because neither was in the "new files" list by name (they were *modified*, not newly created, and easy to overlook). This surfaced immediately and loudly as `ValueError: unknown table` when the Mac's copy of `test_analytics_growth.py`/`test_media.py`/etc. tried to create a `media_brands` row against the *old* `store.py`'s allowlist — caught by running the Mac test suite as part of this same deployment, before declaring the push complete. Fixed by diffing the complete file-by-file MD5 hash listing between the cloud copy and the Mac copy (not just the files I assumed had changed), which found exactly one more drifted file (`store.py`) after the first fix; both are now hash-verified identical. This is the reason the disciplined "verify every file, not just the ones on your list" step matters, and it's now been done for real, twice, on this build.

## End-to-end QA (Section 26)

`scripts/qa_digital_workforce_media_e2e.py` starts a real TTT HQ server (real `ThreadingHTTPServer`, not mocked) against a disposable scratch root, and drives everything over real HTTP:

**Digital Workforce path**: task created → read back → executed (plan → route to `DocumentWorker` → real document created) → reaches `COMPLETED` with non-empty evidence → history readable. A second task of an unregistered type is created and executed to confirm it escalates to `NEEDS_ARYAN` over HTTP rather than crashing the server.

**Media path**: brand created → content item created (starts in `RESEARCH`) → walked through `IDEA` → `CONTENT_PLAN` → `SCRIPT` → a script version created and listed → a publication created, submitted for approval (creates a real `publish_approval` Needs Aryan item), approved → a real publish attempt made via the honest `ManualPublishingChannel`, correctly landing in `FAILED` with a fresh escalation (never falsely `PUBLISHED`) → a real, human-sourced analytics metric recorded → a growth recommendation computed and confirmed honest (`insufficient_data`/`stop`/`test`/`repeat`, never a fabricated number) → a growth experiment created. **No real public content was published** — the script deliberately stops at the honest `FAILED` + escalation state rather than calling `mark-published-manually` with fabricated "proof," since that would require a real post URL the script does not have.

**Today dashboard**: confirmed to include all five new signal keys.

**Restart and persistence (explicitly required by Section 26)**: the HQ server process is killed and a fresh one started against the *same* scratch root; the workforce task, the content item, the publication (still honestly `FAILED`), and the script version are all re-read over fresh HTTP requests and confirmed identical to their pre-restart state — proving real SQLite persistence, not in-memory state that happened to survive.

## Known limitations

Real browser/computer-use automation remains entirely unbuilt by design — every `browser_research`/`browser_action`-type task resolves to `BLOCKED` via `ManualBrowserChannel` and escalates. AI video generation from a prompt and original music composition have no free/local capability today and correctly report `UNAVAILABLE` rather than being faked; video *assembly* from existing images/audio is real. Real publishing to any external platform is unbuilt — every publish attempt resolves to `FAILED` via `ManualPublishingChannel` and requires a human to either build a real adapter later or supply real evidence via `mark_published_manually()`. No paid media provider exists, per the cost policy; `total_cost()` tracking exists and is wired through the data model but is not yet surfaced as its own dashboard aggregate (each asset's individual cost is visible via `/api/media/content/<id>/assets`, and is always $0 today). The TTT HQ UI's new Media/Growth views cover Brands, Content Calendar, Publishing, and Growth Experiments but not a standalone Campaigns view or a standalone Analytics view — campaigns are reachable via `/api/media/campaigns` and analytics via the per-publication route and the Today dashboard's growth signals, which was judged sufficient against "keep the UI simple" for v1; a dedicated view can be added if Aryan wants one. `test_bootstrap.py`'s 15 pre-existing failures are unrelated to this build and remain unresolved in this environment, as in every prior pass.

## What still requires Aryan

Deciding what happens whenever a Workforce task has no capable worker (today, always escalated rather than guessed at). Approving every publication before a publish attempt is even made, and again whenever that attempt fails (today, always, since no real adapter exists) — either by building a real platform adapter, or by supplying real evidence via the manual-fallback path after publishing it themselves. Deciding whether/when to add a paid media provider (video generation, music, or a higher-quality image/voice API) — the cost-approval escalation path exists and is ready, but nothing paid is wired in today. Reviewing and approving real analytics sources before growth recommendations are trusted for a real decision (the system already filters out anything simulated, but a human should still sanity-check a real source the first time it's wired in). Deciding whether the standalone Campaigns/Analytics UI gap above is worth closing.

Task creation, planning, routing to the correct worker, execution, evidence-backed completion, and bounded retry/escalation across the whole Digital Workforce (research, document/spreadsheet creation, email drafting, recurring-workflow scheduling). The entire Media content pipeline's state bookkeeping from research through learn, script versioning, real local image generation (Pillow), real local voice synthesis (ffmpeg+flite), real video slideshow assembly with real captions (ffmpeg/ffprobe), publication lifecycle tracking through the honest manual-fallback gap, real analytics recording from disclosed sources, and real-data-only growth recommendation computation. All of it surfaces through TTT HQ's existing Today dashboard and Needs Aryan queue with zero new approval-UI code, and all of it — proven by the restart-and-persistence check above, on both the cloud workspace and the authoritative Mac environment — survives a real process restart because it is backed by the same real SQLite database every other TTT HQ surface already uses.
