## Scope of this pass

The 24-section specification defines five internal passes (A through E). This pass delivers Pass A in full: the Company Workflow Orchestrator (Section 2), the Application Executor (Section 3), and the Sales Execution groundwork that Sections 7–9 need (Negotiation Guardrails, Client records, the Closing Agent). Passes B through E — Outbound Lead Agent, Outreach Agent, Reply/Conversation Agent, full Client Onboarding, Delivery/Account Management, Billing/Receivables, Retention/Upsell, Sales Manager, and the full TTT HQ UI extension — are explicitly not built yet. Section 22 permits continuing through all five passes without stopping, but a serious integrated build of this size is more honestly delivered and verified one pass at a time than claimed all at once; the report is explicit below about exactly where Pass A ends.

## Architecture

Nothing existing was rebuilt. Two new layers were added on top of the existing Revenue Hunter / Opportunity Agent code, connected to it the same way `ProposalStore` already connects to `NeedsAryanQueue` — by constructor injection, so neither new module imports anything that already imports it back:

**`falguna/lifecycle.py`** — the Company Workflow Orchestrator. It adds one new column (`rh_opportunities.lifecycle_state`) and one new table (`rh_lifecycle_events`) via the existing additive-migration mechanism in `store.py`, so it runs cleanly against the live production database without touching anything else. The 20-state machine named in Section 2 (DISCOVERED through RETAIN/LOST) is layered *on top of* the existing 9-value `stage` field (`PIPELINE_STAGES` in `revenue_hunter.py`) — `stage` is not replaced, not duplicated, and every existing route/test/UI element that reads it keeps working unchanged. `LifecycleOrchestrator.transition()` calls the existing, already-tested `OpportunityStore.move_stage` / `mark_won` / `mark_lost` at the specific boundary points where a fine-grained state has a real coarse-stage equivalent (`QUALIFIED`→"Qualified", `CONTACTED`→"Applied/Sent", `REPLIED`→"Replied", `DISCOVERY_CONVERSATION`→"Meeting", `NEGOTIATING`→"Negotiating"); every other lifecycle state has no coarse-stage equivalent at all and leaves `stage` untouched, exactly as the older field was never designed to track post-Won delivery. Every transition — valid or refused — is checked against an explicit transition graph and either applied or rejected with a `LifecycleError`; there is no path that silently skips a state. A same-state transition is treated as an idempotent no-op (needed because `requalify_all()` re-qualifies opportunities repeatedly) rather than an error.

**`falguna/application_executor.py`** — Section 3. An adapter/provider pattern (`ApplicationChannel` subclasses) rather than one function, because different channels have very different legitimacy and automation surfaces. Full, honest accounting of what exists: `ManualReviewChannel` is the only channel wired in by default, and it never submits anything anywhere — it always resolves to `BLOCKED` (with a specific, closed-set reason such as `ambiguous_consent_required` or `no_application_channel_available`) and raises a Needs Aryan item, because no real browser-automation adapter that has actually been built, audited, and approved for a specific platform exists yet. `SimulatedTestChannel` is the one path that can report `SENT`, and it is explicitly gated behind an `allow_simulated=True` flag that ordinary runtime code never passes — it exists only for tests and the controlled QA run below. `UnsupportedChannel` is the terminal case for a channel name with no adapter, and it always blocks rather than silently no-opping.

**`falguna/sales_ops.py`** — Sections 7–9 groundwork. `SalesPolicyStore` is the exact settings-row pattern `AcquisitionProfileStore` already uses (one row in the existing `rh_settings` table). `evaluate_terms()` is a pure function checking proposed price/currency/discount/upfront-payment/payment-terms/free-revisions/timeline against that policy; `NegotiationGuardrails` wraps it and escalates anything out-of-bounds to the existing `negotiation_response_approval` Needs Aryan kind — no new kind was needed. `ClientStore` is the real `clients` table (idempotent upsert by name), replacing what was previously only a client-name grouping view. `ClosingService.close()` is the Closing Agent: it records the structured deal terms into the new `rh_closing_records` table, marks the opportunity Won through the existing `OpportunityStore.mark_won`, upserts the Client and credits its `total_won_value`, and creates the Active Job through the existing, already-idempotent `ActiveJobStore.create_from_won_opportunity` — composing four already-tested primitives rather than reimplementing any of them. `close()` is itself idempotent: calling it twice for the same opportunity returns the original closing record, client, and active job rather than creating duplicates.

## Lifecycle hooks into existing, tested code

Rather than requiring every caller to remember to call the orchestrator, best-effort hooks (`try_transition`/`try_initialize` — catch `LifecycleError`, return `None`, never raise) were wired directly into the business methods that already existed and were already tested: `OpportunityStore.create()` → DISCOVERED, `QualificationStore.qualify()` → QUALIFIED (unconditionally, mirroring the existing stage-move behavior — an IGNORE recommendation still reaches lifecycle QUALIFIED; deciding to drop it to LOST is a business call left for a later pass, not something this hook does silently), `ProposalStore.generate()` → PITCH_READY, then AWAITING_APPROVAL once a Needs Aryan item exists, and `apply_decision_side_effect()` → APPROVED on an approved proposal, or back to PITCH_READY on rejection/changes-requested. Every one of these takes an optional `orchestrator=` parameter that defaults to `None`, so every existing call site that doesn't pass one (there were many, across `opportunity_agent.py`'s `DiscoveryEngine` and `requalify_all()`) is completely unaffected — this was verified, not assumed: the full pre-existing suite was run before and after wiring the hooks in, with identical results both times. `hq_web.py`'s real HTTP routes were then updated to actually pass a `LifecycleOrchestrator` instance into all of these, so a real discovery run, qualify call, proposal draft, and approval decision through the live server now really do advance `lifecycle_state`, not just in tests.

## New HTTP routes

Six new routes on the existing TTT HQ server, following its existing conventions exactly (same path style, same JSON body shape, same error handling): `GET /api/rh/opportunities/<id>/lifecycle` (current state + full event history), `POST /api/rh/opportunities/<id>/lifecycle/transition` (an explicit, raising transition — for a caller that needs to know whether it actually landed, unlike the best-effort hooks), `POST /api/rh/opportunities/<id>/apply` (drives the Application Executor), `GET`/`POST /api/rh/sales-policy`, `POST /api/rh/opportunities/<id>/negotiation/evaluate`, `POST /api/rh/opportunities/<id>/close` (drives the Closing Service), and `GET /api/rh/clients` / `GET /api/rh/clients/<id>` against the new real `clients` table. The existing `/won` and `/lost` routes were also updated to record the lifecycle transition alongside the coarse stage move they already made.

## Autonomy and approval rules — what is genuinely automated vs. what always stops for Aryan

Everything that touches money, a real external submission, or a term outside a configured policy stops and creates a Needs Aryan item; nothing in this pass sends anything to a client or submits anything to a real external system on its own. Concretely: qualification and proposal drafting were already automatic before this pass and still are (deterministic, template-based, no model call). Applying/sending a proposal always stops at `BLOCKED` today, because `ManualReviewChannel` — the only real channel wired in — has no way to know in advance whether a given job-board URL will demand a CAPTCHA, a login, a legal declaration, or payment, and the specification is explicit that guessing wrong here is not acceptable; it escalates every single time. Proposed negotiation terms outside the saved Sales Policy escalate the same way. Closing a deal, creating the Client record, and creating the Active Job are automatic once Aryan has approved a proposal and terms have been agreed — those are recording/bookkeeping actions on an already-approved deal, not new external actions, matching how `mark_won`/`create_from_won_opportunity` already worked before this pass. The real Falguna handoff (an actual new engineering mission) still requires Aryan to explicitly call `trigger_handoff` with a target repository, exactly as before this pass — nothing here makes that automatic.

## What is real vs. simulated — stated plainly

The full state machine, the Needs Aryan escalation paths, the Sales Policy guardrails, the Client/Closing bookkeeping, and the real Falguna handoff are all genuinely live code paths, verified end-to-end below. The one piece that is explicitly not real yet is outbound application/outreach: `ManualReviewChannel` never actually submits anything to a real website, because no adapter exists yet that has been built and approved for a specific platform's actual submission flow — building that was out of scope for "extend the existing state machine and sales execution," and Section 3 itself asks for exactly this conservative default until such an adapter exists. `SimulatedTestChannel`'s `SENT` result is real code, real audit trail, real lifecycle advancement — but it is explicitly a test/QA-only adapter, gated behind `allow_simulated=True`, and never reachable from an ordinary approve-and-apply call. No reply monitoring, no inbound email/message ingestion, and no real outbound send exist in this codebase at all yet (Sections 4–6, deferred to Pass B).

## Live end-to-end QA (Section 21)

Run against a disposable scratch state.db and a disposable scratch git repository — never against the real production `state.db` — so this run could exercise a real Falguna handoff without any risk to real data. The full chain was walked through real code, not mocks: opportunity created (→ DISCOVERED) → RESEARCHING → real `qualify()` call (→ QUALIFIED) → real `generate()` proposal draft, which created a real Needs Aryan item (→ AWAITING_APPROVAL) → real `NeedsAryanQueue.decide("approve")` plus `apply_decision_side_effect` (→ APPROVED) → real `ApplicationExecutor.apply()` on the explicitly-gated `SimulatedTestChannel` (→ CONTACTED, with `SENT` evidence recorded) → REPLIED → NEGOTIATING → real `ClosingService.close()`, which created a real Client (`total_won_value` credited $1,500), a real Active Job, and marked the opportunity Won (→ ONBOARDING) → a **real** `ActiveJobStore.trigger_handoff()` call against the scratch repo, which returned a real mission id, requirement id, and task id through the same `accept_revenue_hunter_handoff`/`ControlPlane.create_mission` path every other Falguna mission goes through. The store was then closed and reopened fresh (a real restart, not a mock) and every one of those facts — current lifecycle state (`ONBOARDING`), full 12-event history, coarse stage (`Won`), client won-value, active job handoff status (`HANDED_OFF`) and mission id, and the closing record — was re-read from disk and matched exactly. State persistence across a restart is confirmed, not assumed.

## Known limitations

No real outbound application/outreach adapter exists — every application attempt today stops at BLOCKED and asks Aryan. No Reply/Conversation Agent, Negotiation Agent automation, or Outbound Lead Agent exists yet — negotiation terms can be *checked* against policy but nothing drafts or sends a negotiation response. Billing/Receivables, Delivery/Account Management tracking against a live Falguna mission, Retention/Upsell workflow, and the Sales Manager coordination layer (Sections 11–14) do not exist yet. The TTT HQ UI was not extended to surface any of Pass A's new state (Section 15) — every capability above is real and tested at the API/service layer, but nothing new is visible in the browser yet.

## What still requires Aryan

Approving every proposal before anything can be applied to (unchanged from before this pass). Deciding what happens when an application is BLOCKED — today, always. Approving negotiation terms that fall outside the Sales Policy (which currently has no values configured — every term will read as "within policy" until Aryan sets real minimums via `POST /api/rh/sales-policy`). Triggering the real Falguna handoff for a Won opportunity, exactly as before. Building or approving any real application-submission adapter for a specific platform, before that platform's applications can ever move past BLOCKED.
