## Scope

The 24-section specification asked for the first complete vertical slice of the TTT Autonomous Revenue-to-Delivery Loop — Opportunity → Research → Qualification → Proposal → Approval → Application/Outreach → Reply → Negotiation → Won → Client Onboarding → Active Job → Falguna Handoff → Delivery Tracking → Client Update → Billing → Completion → Retention/Upsell — built in five internal passes (A–E), without stopping between passes absent a genuine architectural, credential, legal, or safety blocker. All five passes are complete. This report supersedes the interim Pass A report with the full picture; nothing described in that report was rebuilt or discarded — Passes B–E were built directly on top of the Pass A orchestrator, executor, and sales-ops groundwork exactly as instructed.

No genuine blocker was hit at any point. The one thing that remains permanently gated — real outbound application/outreach submission and real binding commercial acceptance without a configured Sales Policy — is gated by explicit design instruction (Section 3's "no adapter until approved," and the commercial safety default), not by an obstacle encountered along the way.

## Architecture by pass

**Pass A (recap — see the interim report for full detail):** `falguna/lifecycle.py` (Company Workflow Orchestrator, 20-state machine layered on the existing 9-value `stage` field), `falguna/application_executor.py` (channel/adapter pattern; `ManualReviewChannel` always blocks and escalates, `SimulatedTestChannel` is test/QA-only behind `allow_simulated=True`), `falguna/sales_ops.py` (Sales Policy, Negotiation Guardrails, Client records, Closing Agent) with the **commercial safety default**: `DEFAULT_SALES_POLICY` carries a `configured` flag, set `True` only by `SalesPolicyStore.save()`. `ClosingService.close()` branches on it — an unconfigured policy never executes a close; it produces a Needs Aryan "Closing Package" (`ref_type="rh_closing_package"`) via `_prepare_closing_package()`, and only `finalize_pending_closing()` — called when that item is approved — ever actually runs the close. An unconfigured policy cannot accidentally mean unrestricted approval; this is covered by its own regression tests and re-verified in the end-to-end QA below.

**Pass B — Conversation + Negotiation + Closing (`falguna/conversations.py`):** A persistent, deterministic, rule-based Reply Agent — no LLM call anywhere in this module. `classify_intent()` matches ordered literal phrases against `_INTENT_SIGNALS` in a fixed priority order (`rejection`, `meeting_request`, `price_objection`, `timeline_objection`, `scope_clarification`, `requirement_request`, `question`, `interested`, `spam_irrelevant`) — first match wins, so a message ending in `?` classifies as `question` even if it also sounds interested; this is documented, intentional, deterministic behavior, not a bug (it surfaced once during QA script authoring — see Errors and fixes below — and the fix was to the QA script's own test message, not the classifier). `ReplyAgent.generate_reply()` drafts only from real on-file fields (opportunity, qualification, proposal) and returns `None` for `spam_irrelevant`/`other` rather than fabricating a reply. `NegotiationGuardrails` (Pass A) now has a real conversation feed to check terms extracted from.

**Pass C — Onboarding + Delivery (`falguna/onboarding.py`):** A 12-item checklist (`contact_information` through `acceptance_criteria`) with `REQUIRED/RECEIVED/MISSING/BLOCKED` states. `credentials_access` is the one item type marked sensitive (`SENSITIVE_ITEM_TYPES`): `OnboardingStore.set_item()` hard-raises `OnboardingError` if a caller ever passes `value_text` for it — only a `notes` reference (e.g. "shared via 1Password vault") is accepted, and the audit log never records `value_text` for any item, sensitive or not. This is enforced in code, not just documentation, and is covered by a dedicated test asserting the audit log never contains the raw value. `DeliveryBriefService.build()` assembles a structured brief from the closing record, approved proposal, client, and onboarding items only — never fabricated content. `enrich_active_job_payload()` is idempotent: it captures the original Active Job requirement text once (`base_requirement`), then on every call rebuilds an "Additional context from Client Onboarding" section fresh from current onboarding state and re-derives the full requirement — so calling it five times never duplicates text and always reflects the latest onboarding answers. It is wired as a best-effort auto-step (try/except `OnboardingError`) immediately before `ActiveJobStore.trigger_handoff()`, so a real Won → Onboarding → Handoff flow automatically carries onboarding context into the real Falguna mission's requirement text — proven by a test that reads the mission's actual `requirements.body` row after a real handoff, not just the Active Job's own payload.

**Pass D — Account Management + Billing + Retention (`falguna/account_management.py`, `falguna/billing.py`):** `AccountManagerService.status_for_active_job()` reads Falguna's own tables (`missions`, `requirements`, `tasks`, `runs`, `checkpoints`, `supervisor_states`, `approvals`) read-only — the same join pattern `NeedsAryanQueue` already used — and maps real `RunStatus` values to a delivery status; no mission or run on file means `NOT_STARTED`, never an invented "in progress." `client_update_draft()` is grounded entirely in that same evidence — verified by a test that asserts no `%` character ever appears anywhere in a draft, ruling out fabricated completion percentages. `scope_signals()` flags real inbound messages classified `requirement_request`/`scope_clarification` that arrived after closing, as a truthful (not AI-judged) scope-creep signal. `BillingStore.record_payment()` and `CompletionService.record_completion()` both hard-raise if `evidence` is falsy — payment can never be marked received, and delivery can never be marked complete, without something concrete backing it. Payment evidence accumulates as a JSON list, never overwritten, so a partial-then-full payment history is preserved. `check_overdue()` only moves an invoice to `OVERDUE` when a real `due_date` has actually passed, and is an on-demand re-check, never an automatic timer. `RetentionStore` tracks the seven kinds the spec named (maintenance, support/hosting, automation, AI integration, testimonial, referral, follow-up) with real due dates.

**Pass E — Sales Manager + Outbound Foundation + HQ UI (`falguna/sales_manager.py`, `falguna/outbound.py`):** `SalesManagerService` answers the eleven questions Section 13 asked for, aggregating only real on-file data — `_priority_label()` buckets opportunities into plain `High`/`Medium`/`Low` from real signals (qualification recommendation, parsed suggested price, age in days), deliberately never a manufactured decimal probability, per the explicit "avoid fake probability precision" instruction; this is enforced at the code level (`best_leads()` never emits a `probability` key or a `%`) and checked by a test. `OutboundLeadStore.create_lead()` holds one real, researched record per prospect — no bulk import, `confidence` must be a plain `Low/Medium/High` label (a percentage string is rejected outright by `OutboundLeadError`). `OutreachService` is the one place in the whole build that deliberately has **no send path at all**, real or simulated: `draft_message()` always produces a `PREPARED` row and an `outreach_approval` Needs Aryan item; `mark_sent()` requires that item to already be `APPROVED` and only then records that the owner sent the message *themselves*, outside the system — it transmits nothing. This is the conservative choice the spec asked for given cold outbound's higher spam/deception risk relative to replying to an inbound message.

**TTT HQ UI (Section 15):** Two new operational views — Sales Manager (read-only aggregated dashboard: attention items, best leads, who replied, negotiations needing action, what can close soon, onboarding clients, blocked deliveries, overdue invoices, upsell-ready clients) and Outbound Leads (create-lead form, per-lead outreach-draft mini-form) — added to the existing single-page app's `.navitem`/`rhLoaders` pattern. The existing "Active Jobs" nav item was relabeled "Active Jobs / Delivery" rather than duplicated. No cosmetic redesign was done anywhere in the existing UI, per instruction.

## External Action Policy — REAL vs SIMULATED vs PREPARED, enforced in code

- **REAL**: qualification, proposal drafting, lifecycle transitions, Sales Policy evaluation, Client/Closing bookkeeping, onboarding checklist tracking, delivery-brief assembly, account-status reads, billing records, completion records, retention tracking, sales-manager aggregation, and the real Falguna handoff (an actual mission created through `ControlPlane.create_mission`) are all genuinely live code, not mocked.
- **SIMULATED**: `ApplicationExecutor`'s `SimulatedTestChannel` is the only adapter anywhere in this build that can report an outbound `SENT`, and its evidence record explicitly includes `"simulated": True` plus a note — it is gated behind `allow_simulated=True`, which no ordinary runtime call ever passes, and exists purely for tests and the controlled QA run below.
- **PREPARED**: `OutreachService.draft_message()` always produces `PREPARED`, never `SENT` — there is no code path in this module that can transmit a message. `mark_sent()` only ever records an owner's own out-of-band action.

Simulation never appears as real production activity anywhere: the `simulated` flag is explicit and checked by tests; the UI never labels a `PREPARED` draft or a simulated evidence record as sent/delivered.

## Autonomy and Needs Aryan policy

Everything that touches money, a real external submission, or terms outside a configured policy stops for Aryan. Concretely, unchanged from Pass A and extended by B–E: applying to a real opportunity always resolves to `BLOCKED` today (no approved real adapter exists yet — by design, per Section 3); negotiation terms outside the Sales Policy escalate via `NegotiationGuardrails`; **any close attempted while the Sales Policy is unconfigured produces a Needs Aryan closing package rather than executing** — this is the single most important safety property added across this whole build and is covered by nine dedicated regression tests (`ClosingServiceCommercialSafetyDefaultTests`); every outreach draft escalates via `outreach_approval` and cannot be marked sent until approved; every payment and every delivery completion requires explicit evidence, never inferred from a status field. What is genuinely autonomous today: discovery, qualification, proposal drafting, lifecycle tracking, conversation intent classification and reply drafting (draft only — nothing auto-sends a reply either), onboarding checklist bookkeeping, delivery-brief assembly and enrichment, account-status/client-update-draft generation, sales-manager prioritization and reporting, and — once a proposal is approved and a deal's terms are agreed and the Sales Policy is configured — the mechanical bookkeeping of closing, client crediting, and Active Job creation.

The server was restarted mid-QA and every fact above was re-read from disk and matched exactly (real persistence, not assumed). Idempotency was verified at multiple points (repeated close, repeated handoff-enrichment, repeated payment-evidence append, repeated mark-sent correctly rejected). ## Known limitations

Real outbound application submission and real cold outreach transmission remain entirely unbuilt by design — every application attempt still resolves to `BLOCKED`, and outreach drafts can only ever be marked `SENT` by an owner's own manual action, never transmitted by the system. Negotiation is guardrails-plus-reply-drafting, not an autonomous back-and-forth negotiator — every counter-offer still needs a human to actually send it. The Sales Policy ships with no real commercial limits configured; until Aryan sets them via `POST /api/rh/sales-policy`, every close will keep producing a Needs Aryan closing package rather than executing automatically, by design. Billing has no real payment-gateway integration — `record_payment()` records evidence a human supplies, it does not process a transaction. The TTT HQ UI's new views are read-only operational dashboards; there is no in-UI negotiation/reply-composition workspace yet. `test_bootstrap.py`'s 15 pre-existing failures are unrelated to this build but remain unresolved in this environment.

## What still requires Aryan

Approving every proposal before it can be applied to. Deciding what happens whenever an application attempt is `BLOCKED` — today, always. Approving negotiation terms outside the Sales Policy. Configuring real Sales Policy limits at all — until that happens, every closing decision is a Needs Aryan item regardless of terms. Approving every outreach draft before it can be marked sent (and actually sending it — the system never does). Every actual payment collection and every actual message send to a client or prospect. Triggering the real Falguna handoff for a Won opportunity (automatic onboarding-context enrichment happens once triggered, but triggering itself is still Aryan's call).

## What is genuinely autonomous today

Opportunity discovery and extraction, qualification and its recommendation/why, proposal drafting, the full 20-state lifecycle tracking with a real event history, inbound-message intent classification and reply drafting (draft only), onboarding checklist bookkeeping with hard sensitive-value protection, delivery-brief assembly and idempotent enrichment into real Falguna missions, account-status reporting grounded purely in real mission/run evidence, client-update drafting with a code-enforced no-fabricated-percentage guarantee, sales-manager prioritization and the eleven-question attention/pipeline report, and — once Aryan has approved a proposal, agreed terms, and configured real commercial limits — the mechanical bookkeeping chain from closing through client crediting, Active Job creation, and Falguna handoff triggering (the trigger call itself still needs Aryan).
